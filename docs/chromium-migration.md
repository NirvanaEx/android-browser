# Chromium: цель и эталон

Ветка `codex/chromium` создана 28 сентября 2026 по запросу пользователя.
Основа — `b815938`, отдельная рабочая папка; незакоммиченные изменения
основной Firefox-ветки не переносились и не изменялись.

Цель — захват и весь видеоплеер как в предоставленном Banana Browser.
Нужно сохранять исходное воспроизведение, обеспечивать плавный вход/выход,
нативное управление, жесты, масштаб, ориентацию, скорость и функции плеера
эталона. Метаданные и SHA-256 эталона: `tools/chromium/reference.json`.

## Что установлено

Android-часть Banana получает готовые Mojo-объекты от Chromium. Кнопка
отправляет команду `BananaMediaButtonController`, события передают
`BananaMediaCommandProcessor`, над браузером открывается прозрачный dialog.
Play/Pause/Seek/масштаб используют внутренний канал движка. Для некоторых
дополнительных функций есть JS сайта (например, качество и субтитры YouTube).

В исследованной цепочке основной вход не экспортирует URL в отдельный
Android-декодер. Это не доказывает поведение каждого сайта или алгоритм
выбора нескольких видео: нативная часть пока не восстановлена.

Полный локальный разбор хранится вне Git в
`D:/Projects/Personal/apk-analysis/banana-20.15/`.

## Приёмка

Нельзя объявлять результат «1 в 1» на основании компиляции или DOM-тестов.
Нужны одинаковые сценарии на одном Android-устройстве для эталона и Upgrid:

- HTTP MP4, blob/MSE и iframe: реальный кадр и движение времени;
- несколько video, играющий/пауза, смена источника и навигация;
- вход/выход: нет перезапуска потока, непреднамеренной паузы или скачка позиции;
- Play/Pause, перемотка, скорость, масштаб, ориентация и блокировка controls;
- все доступные в эталоне кнопки, включая PiP, loop, качество и субтитры;
- фон, смена вкладки, возврат и холодный запуск с восстановленной вкладкой;
- реальные задержки входа, пропуски кадров и непрерывность звука.

Недоступные или непроверенные возможности должны быть перечислены явно.
Промежуточные и непроверенные APK не являются готовым выпуском и не публикуются.

### Измерение перехода на тестовом ролике

`tools/tests/fixtures/player-workbench.html` поддерживает окно измерения:
после устойчивого воспроизведения нажать **Start comparison window**, выполнить
вход и выход из нативного плеера, затем **Finish comparison window**. Для обоих
браузеров нужны одинаковые файл, телефон, ориентация, скорость и сценарий.
Использовать короткие имена запуска, например `banana-mp4` и `upgrid-mp4`.

Локальный `/probe-events` сохраняет `windowLoads` и `windowPauses`, количество
кадров и `getVideoPlaybackQuality()` (если доступно), а также наибольший интервал
между `requestVideoFrameCallback`. Последний показатель зависит и от работы
JavaScript, поэтому сам по себе не доказывает пропуск декодером. Не смешивать
обычный вход/выход с проверкой фона или намеренной перемотки. Отсутствующие
счётчики сохраняются как `null`, а не как ноль пропущенных кадров.

Текущие GN args создают debug-сборку для проверки интеграции. Её можно использовать
для поиска перезапуска видео, ошибок источника и lifecycle, но итоговое сравнение
производительности с релизным Banana требует оптимизированной сборки Upgrid.

HTTP-проверка сервера с `kind=protocol-selftest` — только проверка формата данных.
Такие записи не являются Android-измерением и не включаются в сравнение.

## Ресурсы

Согласованный WSL-профиль остаётся 6 ГБ RAM / 4 CPU / 8 ГБ swap. Не менять
его автоматически. Документация Chromium указывает минимум 8 ГБ RAM и
100 ГБ диска для Android-сборки. На момент проверки C: свободно около
145 ГиБ, D: около 71 ГиБ; WSL VHD находится на C:. Виртуально свободное
место внутри WSL нельзя считать доступным физическим местом хоста.

Источник требований:
https://chromium.googlesource.com/chromium/src/+/main/docs/android_build_instructions.md

## Статус

Ветка и эталон подготовлены. Написан исходный прототип цепочки Blink → Mojo →
browser process → Android dialog. Генерация GN и компиляция интеграционных целей
прошли: C++-мост, изменённые Blink-модули и Java плеера. Полный APK и проверки
на Android ещё не завершены. Этот код пока не является рабочим релизом.
Проверки ориентации в Robolectric прошли 10/10 (SDK 29/36); они не заменяют
проверки плеера на устройстве. Полная сборка APK запущена после них.
Пользователь выбрал собственный исходный проект Chromium. Перепаковка APK
не является согласованным результатом. Реализуется собственный канал управления
в Blink; исходный нативный алгоритм Banana не объявляется восстановленным.

Пользователь отдельно разрешил временные 8 ГБ RAM WSL для этой сборки.
CPU=4 и swap=8 ГБ сохранены. Исходный файл конфигурации сохранён в
`build/chromium/wslconfig-before-8gb`; после окончания сборочной работы
необходимо восстановить его на безопасной границе без работающих процессов.

### Оставшиеся отличия

В прототипе есть код выбора видео, fullscreen, основных команд, жестов,
масштаба, ручного поворота, блокировки кнопок и HTML-дорожек субтитров,
скачивания поддерживаемого HTTP-файла и вызова стандартных Chromium PiP/Cast.
Это описание написанного кода, а не подтверждение его работы на Android.
PiP/Cast зависят от доступности штатного backend Chromium на устройстве.
Для качества и собственных субтитров YouTube написан адаптер API выбранного
плеера; изолированные Node-тесты проходят, на сайте он ещё не проверен.
Не реализованы скачивание MSE/YouTube, отдельный YouTube Cast и SponsorBlock.
Нет сравнительного замера задержек
и пропусков кадров. Внешний вид панели пока не воспроизводит эталон.
Кнопка звука пока переключает `muted` выбранного video; в исследованном Banana
она переключает системный `STREAM_MUSIC`. Это наблюдаемое отличие, которое
нужно учитывать при проверке вместе с аппаратными кнопками громкости.

Firefox WebExtensions, uBO и настройки прежнего Upgrid автоматически в Chromium
не перенесены. Исходная ветка Fenix сохранена. Поддержка блокировки рекламы
и остальных обязательных функций браузера остаётся условием готового выпуска.
Chromium 146 используется только для разработки по эталону; перед выпуском
нужен переход на поддерживаемую базу с актуальными исправлениями безопасности.
