# Upgrid на ПК

Локальный стенд запускает настоящий Android APK Upgrid в отдельном постоянном
эмуляторе `Upgrid_PC`, а не веб-макет браузера. Он нужен для ручного воспроизведения
ошибок, проверки изменений и записи состояния в момент сбоя.

[Результаты проверки 27.09.2026 и известное ограничение первого запуска](VALIDATION.md).

Из корня репозитория откройте **`Upgrid-PC.cmd`** двойным щелчком. В меню:

1. **Открыть тестовое устройство** — открывает Android и уже установленный Upgrid.
   На пустом устройстве устанавливает последний успешно собранный этим стендом APK.
2. **Собрать текущий код и запустить** — применяет существующий Fenix overlay,
   выполняет инкрементальную x86_64 debug-сборку в WSL и обновляет приложение через
   `adb install -r`. Вкладки, настройки и данные тестового профиля сохраняются.
3. **Следить за кодом** — ждёт окончания редактирования, пересобирает и обновляет
   браузер после изменений в `app/src/main/`, `tools/fenix/` или профиле сборки ПК. Первый запуск также
   выполняет сборку. Ошибка сборки оставляет установленное приложение на месте.
4. **Открыть список тестовых страниц** — видео, fullscreen, iframe, несколько видео,
   вкладки, перевод и прокрутка. Обычные сайты доступны через адресную строку.
5. **Сохранить отчёт о баге** — создаёт папку и ZIP с PNG, деревом интерфейса, последними
   логами, состоянием Activity/памяти, версией и квитанцией установленного APK.
   Допишите действия и ожидаемый результат в `steps.txt`; ZIP содержит версию отчёта
   на момент создания. Его можно приложить к сообщению о баге.
6. **Холодный запуск** — завершает процесс Upgrid и открывает его снова, сохраняя профиль.

Закрытие меню оставляет устройство открытым. Пункт 8 закрывает только `Upgrid_PC`.
Локальный сервер тестовых страниц остаётся доступным на loopback:8876 и переиспользуется
при следующем запуске; он не принимает команды управления ПК.

## Команды

Из PowerShell в корне репозитория:

```powershell
.\tools\pc-lab\Start.ps1 -Action status
.\tools\pc-lab\Start.ps1 -Action start
.\tools\pc-lab\Start.ps1 -Action build
.\tools\pc-lab\Start.ps1 -Action watch
.\tools\pc-lab\Start.ps1 -Action open -Page engine
.\tools\pc-lab\Start.ps1 -Action capture -Note 'После возврата из плеера исчезла панель'
```

Чтобы воспроизвести ошибку конкретного выпуска, передайте **его точный APK**:

```powershell
.\tools\pc-lab\Start.ps1 -Action start -Apk 'D:\path\upgrid-arm64.apk'
```

Установка не понижает версию и не удаляет приложение при конфликте подписи.
Такая ошибка выводится явно, без очистки данных. `start` сохраняет выбранную версию;
для перехода на новый код используйте `build`/`watch`, для выбора другого APK —
`-Apk`. Совпадение номера версии само по себе не доказывает совпадение кода:
сравнивайте также SHA-256 и квитанцию.

Дополнительные команды `save` и `restore` сохраняют и восстанавливают snapshot
`upgrid-repro`. **Restore откатывает всё тестовое устройство**, включая установленный
APK и данные, к сохранённому моменту. Он не откатывает код ПК или сервер тестовых
страниц и не фиксирует внешние сайты. Сохранённая квитанция установки после отката
может относиться к более новой версии; `report.json` содержит текущую версию и хеш
установленного APK отдельно и отмечает совпадение с квитанцией.

## Как здесь работает обновление

Изменение HTML тестовой страницы видно после её обновления в браузере: сервер
отдаёт файлы с `Cache-Control: no-store`. Изменения Kotlin, ресурсов и встроенного
WebExtension требуют сборки APK и перезапуска приложения; это **не hot reload**.
Время зависит от Gradle и затронутых файлов. Перед сборкой создаётся проверенная
копия исходников в `build/fenix/pc-lab/sources/`; APK собирается только из неё.
Редактирование проекта во время компиляции не смешивает версии кода: watch поставит
следующие изменения в очередь после текущей установки. Ошибка сборки или изменение
самой сохранённой копии оставляет установленный APK на месте. Путь копии и её хеш
записаны в `build.json` и в отчёте о баге.

Watch запускайте на время работы в отдельном терминале. Ctrl+C останавливает
наблюдение; если в этот момент шла сборка WSL, она может продолжаться. `status`
покажет её, следующий запуск не станет менять занятый checkout.
Режим watch также ждёт общую блокировку `operation.lock`, если её держит другая
проверка, и повторяет проверку после временной ошибки связи с WSL. Блокировку
не нужно удалять вручную: Windows освобождает её при завершении владельца.
Команды уже запущенного устройства используют отдельную `device.lock`, поэтому
открытие страниц и сохранение отчётов доступны и во время другой сборки.

## Среда и ограничения

- Windows, Python 3.11+, Node.js, Android SDK и уже установленный образ Android 34
  Google APIs x86_64. WSL Ubuntu с подготовленным checkout Firefox из `tools/fenix/`.
  Путь SDK берётся из `ANDROID_SDK_ROOT`, `ANDROID_HOME` или `%LOCALAPPDATA%/Android/Sdk`.
- Эмулятор: **2048 МБ RAM, 2 ядра, BelowNormal**, экран 720×1280 / 320 dpi.
  Помимо `-memory 2048` передаётся `-qemu -m 2048`: Emulator 37.1.11 иначе сам
  поднимает память Android 34 до 2560 МБ. Фактическая память гостя видна в
  `/proc/meminfo` и сохраняется в отчёте; текущий работающий эмулятор не перезапускается
  ради применения параметров.
  Отдельный профиль: `build/fenix/pc-lab/avd/`; ADB: `emulator-5580`.
  Существующие AVD и физические телефоны не изменяются.
  ADB reverse связывает порт 8766 только этого устройства с портом 8876 ПК; сервер
  обычных тестов на порту 8766 ПК не используется, его сценарии отказа изолированы.
- Сборка: `tools/pc-lab/build.sh`, тот же Firefox pin и Fenix overlay,
  **1 Gradle worker, heap 4 ГБ, metaspace 1 ГБ**.
  Используется `--no-daemon`: процесс Gradle завершится после сборки и освободит
  память для Android. Инкрементальные результаты и кеши на диске сохраняются.
  Глобальный профиль WSL не меняется. Пока идёт другая Fenix-сборка, новая не запускается;
  во время release-оптимизации стенд не запускает новый эмулятор.
- PC-сборка использует **настоящий x86_64 Gecko**, отдельно от телефонной ARM64-сборки.
  Отдельный checkout — `~/.cache/upgrid/firefox-pc-155.0.1` внутри WSL
  (переопределяется `UPGRID_PC_FENIX_DIR`). Он создаётся из закреплённого коммита,
  без переноса незавершённых изменений телефонной сборки. Объектные файлы находятся
  в его `objdir-upgrid-pc`; первая
  сборка загружает соответствующий бинарный артефакт Gecko. Папка телефонной сборки
  `objdir-upgrid` не используется и не меняет архитектуру.
  Обычный x86_64 split из телефонной сборки не подходит: в нём нет x86_64 Gecko.
  Установщик проверяет именно наличие `libxul.so` нужной архитектуры в APK.
- Для проверки выпущенного ARM64 APK можно передать `-Apk`; образ должен поддерживать
  ARM64-трансляцию, что установщик проверяет. Эта трансляция тяжёлая: на первоначальном
  прогоне ARM64 debug появилась белая страница и нехватка памяти, тогда как release
  загрузил страницу и кадр плеера. Поэтому основной режим разработки использует x86_64.
  Эмулятор и другая архитектура не подходят для сравнения FPS с телефоном.
- Видео требуют `build/fenix/sample.mp4` и для отдельных сценариев соседних синтетических
  роликов, описанных в `tools/fenix/README.md`. Их отсутствие выводится при запуске.
- Для надёжного дерева интерфейса соберите существующий helper командой
  `tools/tests/android-ui/build.ps1`; без него используется `uiautomator dump`, который
  может не успевать при непрерывной анимации. Остальная часть отчёта сохраняется.
- Отчёты находятся в `build/fenix/pc-lab/reports/` и автоматически никуда не отправляются.
  Скриншоты/логи могут содержать открытые тестовые страницы. В самом APK сохраняется
  существующая настройка технической диагностики проекта.

**Не все телефонные ошибки воспроизводимы:** аппаратные кодеки, DRM, видеодрайверы,
прошивки, конкретная сеть и аккаунт сайта могут вести себя иначе. Для таких ошибок
нужно повторение на исходном телефоне. Эмулятор позволяет повторять действия и
проверять регрессии, но не доказывает исправление на каждом устройстве.

Этот стенд не создаёт публичный выпуск: `release.json` не меняется, публикация
в Telegram не выполняется. У готового пользовательского релиза остаются обычные
обязательные проверки и правила публикации из AGENTS.md.

Справка Android: [параметры эмулятора](https://developer.android.com/studio/run/emulator-commandline),
[ограничения Apply Changes](https://developer.android.com/studio/run#apply-changes).

Проверки управляющего инструмента:

```powershell
python -m unittest discover -s tools/pc-lab -p 'test_*.py' -v
```
