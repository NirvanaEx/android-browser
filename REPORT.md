# Уязвимости — android-browser — 2026-08-16

## Что сделано

### 1. Сохранённый пароль отдавался не тому сайту, который его просил

- **Файл:** `app/src/main/assets/extensions/upgrid_fullscreen/background.js:66`
  (`PAGE_COMMANDS` / `sendToPage`), `app/src/main/assets/extensions/upgrid_fullscreen/logins.js:150`,
  `app/src/main/java/com/upgrid/browser/MainActivity.kt:1060`
- **Зачем:** `loginFill` лежал в `PAGE_COMMANDS` и уходил через `sendToPage`,
  то есть **в активную вкладку**, а если ни одна вкладка не помечена активной
  для расширений (`markActiveForWebExtensions` ещё не отработал — первая
  отрисовка, восстановленная сессия) — то, по задуманному фолбэку,
  `browser.tabs.query({})` **во все вкладки сразу**. При этом запрос на
  автозаполнение приходит откуда угодно: `logins.js` шлёт `action:"ready"` по
  событию `load` в любой вкладке, хоть фоновой, а нативная сторона в ответе не
  знала и не сообщала, кому именно предназначен пароль. Плюс
  `VideoPlayerBridge.sendCommand` кладёт команду в очередь, когда порт лежит,
  и отдаёт её позже — уже на другой странице.

  **Как эксплуатируется.** Пользователь на `attacker.example` долгим тапом по
  ссылке выбирает «Открыть в новой вкладке» (`LinkContextMenu.kt:171`,
  `selectTab = false` — вкладка фоновая) для `https://github.com/login`, либо
  просто оставляет догружаться фоновую вкладку с формой входа. Фоновая вкладка
  дозагружается, `logins.js` в ней объявляет `ready` с `host: github.com`,
  `MainActivity.onLoginEvent` достаёт сохранённую пару и шлёт `loginFill`,
  а `sendToPage` доставляет её **в активную вкладку — на `attacker.example`**.
  Скрипт страницы читает `input.value` у полей логина и пароля (значения
  проставляются штатным сеттером и видны обычному JS страницы) и отправляет их
  куда угодно. Второй, ещё более простой вариант: пока ни одна вкладка не
  «активна» для расширений, тот же пароль рассылается **во все** открытые
  вкладки без разбора.
- **Что изменилось для пользователя или для кода:** ответ с паролем теперь
  адресно уходит во вкладку, которая его запросила (`sendLoginFill`,
  один ответ на один запрос), а `logins.js` дополнительно вставляет пару
  только если `host` в команде совпадает с `location.hostname` документа
  (нормализация как на нативной стороне — нижний регистр, без `www.`);
  нативная сторона этот `host` теперь передаёт. Автозаполнение на «своём»
  сайте работает как прежде и больше не зависит от того, успел ли
  `markActiveForWebExtensions` пометить вкладку.
- **Как проверить:** сохранить пароль на сайте A; открыть сайт B, с него
  долгим тапом открыть страницу входа сайта A в фоновой вкладке; дождаться
  загрузки фоновой вкладки, оставаясь на B. До правки поля входа на B
  заполнялись паролем от A, после — остаются пустыми. Переход на вкладку с A
  заполняет форму как обычно. Собрать и прогнать на устройстве не мог
  (в контейнере нет JDK и Android SDK); JS-часть проверена `node --check`.

### 2. Любое приложение на телефоне могло открыть в браузере `file://`

- **Файл:** `app/src/main/java/com/upgrid/browser/MainActivity.kt:2942`
  (`Intent.dataStringIfView`)
- **Зачем:** `MainActivity` объявлена `android:exported="true"`
  (`AndroidManifest.xml:80`), а `intent-filter` со схемами `http`/`https`
  ограничивает только **неявные** интенты. Хелпер брал `dataString` как есть,
  без проверки схемы, и отдавал его в `tabsUseCases.addTab`.

  **Как эксплуатируется.** Любое установленное приложение — без единого
  разрешения — вызывает явный интент:

  ```java
  Intent i = new Intent(Intent.ACTION_VIEW,
      Uri.parse("file:///data/data/com.upgrid.browser/shared_prefs/upgrid_logins.xml"));
  i.setClassName("com.upgrid.browser", "com.upgrid.browser.MainActivity");
  startActivity(i);
  ```

  Браузер открывает новую вкладку и рендерит файл — читает его собственным
  uid, потому что читает его сам. Так на экран (и в историю, и в превью
  вкладки) попадает приватное хранилище приложения: зашифрованные блобы
  паролей и аккаунта, `shared_prefs`, сессия. Тем же способом достаются
  внутренние `resource://android/assets/…` и страницы `about:`.
- **Что изменилось для пользователя или для кода:** из интента принимаются
  только `http` и `https` — ровно то, что обещает манифест; всё остальное
  отбрасывается, и вызывающий получает стартовую страницу. Обычное открытие
  ссылок из других приложений не затронуто.
- **Как проверить:** `adb shell am start -a android.intent.action.VIEW -d
  "file:///data/data/com.upgrid.browser/shared_prefs/upgrid_logins.xml"
  -n com.upgrid.browser/.MainActivity` — до правки содержимое файла
  отображается во вкладке, после открывается стартовая страница. Та же команда
  с `-d https://example.com` открывает сайт в обоих случаях. На устройстве не
  запускал по причине выше.

## Не делал

- **Пароль по умолчанию `superadmin` / `123`** (`AccountStore.kt:240`) — это
  зашитый в код учётный пароль, и он реально слабый, но эксплуатируется только
  с разблокированного телефона владельца, а починка (принудительная смена при
  первом входе) — продуктовое решение, которое может запереть владельца
  снаружи. Оставляю человеку.
- **`AccountApi.profileUrl` не экранирует логин** (`AccountApi.kt:101`): логин
  подставляется в путь как есть, так что `../` уводит запрос на другой путь
  того же сервера. Хост подменить нельзя, а логин вводит сам владелец
  устройства — внятного «как эксплуатируется» не получилось.
- **`error.js`: `location.href = q.get("u")` на привилегированной странице**
  (`assets/error.js:46`). `resource://`-документ системно привилегирован, и
  переход по адресу из параметра выглядит опасно, но подобрать сценарий, при
  котором в `u` окажется `javascript:` (движок должен отдать `onLoadError`
  именно для такого URI), я не смог — без устройства это подозрение, а не
  находка.
- **`FileNames.sanitize` не убирает имя `..`** (`FileNames.kt:59`): разделители
  пути вырезаются, а голое `..` доживает до `File(directory, name)`. Записи вне
  каталога это не даёт (открытие потока на каталог падает), поэтому не трогал.
- **Автозаполнение без действия пользователя как таковое**: пароль
  подставляется по факту наличия поля, так что любой XSS на самом сайте
  забирает его молча. Это дизайн фичи, а не дефект одной строки — менять надо
  вместе с UI (подстановка по тапу), это отдельный заход.
