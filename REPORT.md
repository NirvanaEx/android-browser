# Поиск ошибок — android-browser — 2026-08-16

Проект — Android/Kotlin, а не Node, поэтому категории из задания читались по
аналогии: «падение процесса» → краш активити/ANR, «гонки» → одновременная
запись состояния из разных корутин, «тихая порча данных» → потерянная или
записанная не туда пользовательская информация.

## Что сделано

### 1. Приватные вкладки писали поисковые запросы на диск

- **Файл:** `app/src/main/java/com/upgrid/browser/MainActivity.kt:706`,
  `MainActivity.kt:960`, хелпер — `MainActivity.kt:760`
- **Зачем:** приватный режим (коммит `0e86fa1`) закрыт в трёх местах из
  четырёх. `recordVisit` проверяет `content.private` перед записью в историю,
  `promptSaveLogin` — перед предложением сохранить пароль, а два писателя
  омнибара — нет. И `wireUrlCommit` (ввод с клавиатуры), и `onSuggestionPicked`
  (тап по подсказке) звали `searchHistory.record(...)` безусловно.
  `SearchHistory` — это `SharedPreferences`, то есть открытым текстом на диск,
  и `SuggestionSource.local()` читает этот список обратно в выпадашку. KDoc
  `openPrivateTab` при этом утверждал, что «нигде ничего не остаётся».
- **Когда ломается:** открыть приватную вкладку → напечатать в адресной строке
  `как вывести пятно с дивана` → Enter. Запрос уходит в `upgrid_vpn`-соседний
  файл `upgrid_history/queries` и переживает и закрытие вкладки, и перезапуск
  приложения. Дальше: открыть обычную вкладку, тапнуть адресную строку,
  напечатать `как` — запрос из приватной сессии стоит в подсказках с иконкой
  часов. Тот же путь через тап по подсказке-завершению вместо Enter.
- **Что изменилось для пользователя:** запрос, набранный в приватной вкладке,
  больше не сохраняется и не всплывает в подсказках обычной вкладки. Обычные
  вкладки ведут себя ровно как раньше.
- **Как проверить:** приватная вкладка → поисковый запрос → Enter → закрыть
  вкладку → обычная вкладка → начать печатать первые буквы запроса: строки в
  выпадашке быть не должно. Контроль: тот же запрос из обычной вкладки —
  строка появляется.

### 2. Две одновременные загрузки затирали записи друг друга

- **Файл:** `app/src/main/java/com/upgrid/browser/download/DownloadRecords.kt:71`
  (`add`), `:76` (`update`), `:91` (`remove`), `:104` (`failInterrupted`),
  `:126` (`persist`)
- **Зачем:** `DownloadManager.start()` запускает `perform()` отдельной корутиной
  на `Dispatchers.IO` для каждой загрузки, то есть несколько загрузок правят
  список из разных потоков. Все мутации были парой «прочитать `state.value` →
  посчитать → присвоить», что не атомарно: изменение, легшее между чтением и
  записью, теряется. `copy()` при этом дёргает `update(..., durable = false)`
  до четырёх раз в секунду, так что окно для гонки открыто всю загрузку.
  `persist()` тоже перечитывал `state.value` заново, поэтому на диск могла лечь
  версия старее той, что уже в памяти.
- **Когда ломается:** начать загрузку A (большой файл, тикает прогресс каждые
  250 мс) и загрузку B. A завершается: `perform` пишет `status = DONE`,
  `uri`, `path`, `bytes`. Ровно в этот момент тик прогресса B, посчитанный от
  снимка списка, взятого до записи A, присваивается последним — строка A
  возвращается в `RUNNING` с пустыми `uri` и `path`. Повторной записи не будет:
  `perform` для A уже вышел. Файл лежит на диске и открывается из системного
  списка загрузок, а в экране «Загрузки» он навсегда «качается», и тапнуть по
  нему нельзя — открывать нечего. После перезапуска `failInterrupted()`
  переводит его в FAILED, то есть удавшаяся загрузка отображается как
  провалившаяся.
- **Что изменилось для кода:** все мутации идут через `state.updateAndGet {}`
  (CAS-цикл), а `persist` получает записанный список параметром, а не читает
  его заново. Поведение при одной загрузке не меняется.
- **Как проверить:** не проверял запуском — в этом окружении нет JDK
  (`java: command not found`), собрать APK нечем. Проверка на устройстве:
  запустить две загрузки крупных файлов одновременно, дождаться конца обеих,
  открыть «Загрузки» — обе строки должны быть завершёнными и открываться;
  перезапустить приложение — обе должны остаться завершёнными.

## Не делал

- **`BrowsingDataCleaner.clear()` игнорирует период для поисковых запросов**
  (`privacy/BrowsingDataCleaner.kt:64`). KDoc класса утверждает: «Our own tables
  — history, past searches — have timestamps, so "the last week" is exact». Для
  истории это правда, для поиска — нет: `SearchHistory` хранит голый список
  строк без единой отметки времени, и `clear()` сносит все 50 записей. Выбрать
  «очистить поисковые запросы за последний день» — потерять всю историю
  поиска. То же и с паролями (`:65`), но там период спорно вообще применим.
  Честное исправление — добавить в `SearchHistory` отметки времени и миграцию
  формата хранения; это смена формата на диске, отдельная правка с отдельной
  проверкой, а не довесок к этому прогону.
- **Карты в `MainActivity`, ключёванные по id вкладки, не чистятся при её
  закрытии**: `lastRecordedVisit`, `pageLoadedAt`, `loadingTabs`,
  `staleDismissed`, `crashRestores` (`MainActivity.kt:193`, `:241`, `:330`,
  `:333`, `:336`). Комментарий у `lastRecordedVisit` обещает «Bounded by the
  open tab count», но снимает записи только пересоздание активити. Утечка
  реальная, но это несколько десятков байт на закрытую вкладку за сессию —
  сценария, где это что-то ломает, я построить не смог, а под правило «уже
  происходит в проде, а не теоретически» это не подходит.
- **`TranslateController` держит `giveUp` в `Handler` до 30 секунд после
  `close()`** (`translate/TranslateController.kt:87`): `onPageChanged()`
  снимает колбэк, `close()` — нет, так что при уничтожении активити с открытым
  переводом ссылка на binding и всё дерево вью живут до срабатывания таймаута.
  Мелко и не наблюдаемо пользователем.
- **`SuggestionSource.local()` может вернуть 10 строк при `MAX_TOTAL = 9`**
  (`search/Suggestions.kt:101`–`149`): 3 закладки + 4 истории + 2 поиска +
  строка «искать как набрано». Краша нет — `merge()` уже прикрыт
  `.coerceAtLeast(0)`, — это лишняя строка в выпадашке, косметика.

## Тесты

Тестов в проекте нет: ни `app/src/test`, ни `app/src/androidTest` не
существует (`ls app/src/` → только `main`).

Собрать проект тоже не удалось: в окружении нет JDK (`java: command not
found`), а `gradlew` без него не запускается. По CLAUDE.md сборка и так живёт в
GitHub Actions, а не локально — Gradle с Gecko требует больше памяти, чем есть.
Обе правки поэтому вычитаны глазами, а не скомпилированы; ниже — что именно
проверялось вручную:

- `kotlinx.coroutines.flow.updateAndGet` существует в 1.9.0 (версия пришпилена
  в `app/build.gradle.kts:252`), импорт добавлен.
- Не осталось ни одного вызова `persist()` без аргумента и ни одного
  `state.value = ...` в `DownloadRecords`, кроме безусловного в `clear()`.
- `inPrivateTab()` объявлен один раз и вызывается из двух мест.
- Проверка на NUL-байты из шпаргалки CLAUDE.md
  (`git ls-files -z | xargs -0 grep -lP '\x00'`) — чисто, ни одного файла.
