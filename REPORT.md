# Ревью android-browser — 2026-08-14

## Что починено

### 1. Гонка в DownloadRecords.update() теряет обновления при параллельных загрузках
- **Файл:** `app/src/main/java/com/upgrid/browser/download/DownloadRecords.kt:67-74` (было)
- **Что не так:** `update()` делал `state.value.map { ... }` и затем `state.value = updated` без какой-либо синхронизации — классический read-modify-write без блокировки.
- **Когда ломается:** `DownloadManager.start()` (`download/DownloadManager.kt:80-89`) запускает по одной корутине на каждую активную загрузку на `Dispatchers.IO` — это реальные параллельные потоки. Каждая загрузка каждые ~250 мс шлёт tick прогресса через `records.update(..., durable = false)`, а по завершении — финальный `DONE`/`FAILED`. При двух одновременных загрузках поток A читает список, готовит запись `DONE` для A; поток B в этот момент читает тот же (ещё не обновлённый) список и пишет свой tick прогресса, затирая только что записанный `DONE` от A. Итог: спиннер зависшей загрузки, которая на самом деле уже дописана на диск, или потерянный статус `FAILED`.
- **Как починено:** добавлена блокировка (`synchronized(lock)`) вокруг чтения-и-записи `state.value` во всех мутирующих методах (`add`, `update`, `remove`, `clear`, `failInterrupted`), запись в prefs (`persist()`) вызывается уже после снятия блокировки, как раньше.

## Не чинил

- **`FileNames.withExtension` может дать имя вида `.pdf`** (`download/FileNames.kt:71-78`) при `Content-Disposition: filename=".."` — сервер целиком из точек. Путь не выходит за пределы каталога загрузок (сепараторы уже вырезаны в `sanitize`), это не уязвимость, а просто странное скрытое имя файла — низкая серьёзность, оставлено следующему прогону.
- **`LoginsActivity.render()` синхронно читает и расшифровывает все логины на главном потоке** (`logins/LoginsActivity.kt:62`, `logins/LoginStore.kt:101-121` — AndroidKeyStore + AES-GCM + JSON на каждый рендер). Потенциальный джанк/ANR при большом числе сохранённых паролей (до 500), но это не даёт неверный результат — оставлено, так как перенос на IO-поток шире 300-строчного бюджета одной находки за корректный результат не отвечает.
- **`AccountSync` при ошибке слияния истории после успешного слияния закладок** (`sync/AccountSync.kt` ~196-222) — гипотеза о рассинхронизации локальных данных и удалённого документа при частичном сбое; не нашёл конкретного входа, воспроизводящего порчу данных с уверенностью — оставлено как догадка.

## Тесты

Тестов в проекте нет (Gradle-сборка требует памяти, которой нет вне GitHub Actions — см. CLAUDE.md, поэтому сборка не прогонялась локально). Изменение просмотрено вручную: добавлена только блокировка вокруг существующих присваиваний `state.value`, сигнатуры и логика вызовов не менялись.
